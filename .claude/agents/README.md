# Agents

Project subagents for DevDigest. Each `*.md` file here is the source of truth for its agent: the frontmatter configures the Claude Code subagent (tools, model, permissions, preloaded skills, hooks), and the body holds its procedure and output templates. This README is only a map — read the agent file for the actual rules.

## Flow

**Current way to run it:** `spec-creator` and `implementation-planner` are run **manually**; everything after an approved plan is automated by [`/run-plan <plan path>`](../skills/run-plan/SKILL.md): implementer → check gate → test-writer (one per `TW-*` row) → architecture-review fix loop (recheck mode) → plan-verifier + security-pass fix loop → doc-writer, then hands `/pr-self-review` to the user (the skill is user-invoked only), at most 2 fix rounds per loop, findings ledger in `.claude/sdd-runs/`. `/run-plan --no-tests` skips test-writer (tests deferred, plan-verifier gets `Tests deferred`). The full flow below is the reference.

`spec-creator` round 1 (for a new user-facing feature: design analysis, draft spec, questions and UX proposals; optionally first a `Research requests` block → main session runs one `researcher` per request in parallel → resume `spec-creator` with the reports) → main session asks the user → `spec-creator` round 2 (finalised `specs/<module>/SPEC-NN-<slug>.md`) → main session asks the user in chat to approve the spec → on "approve" the main session sets `Status: approved` (on "changes" → back to `spec-creator`) → `researcher` (optional, any time; for a feature, a **context pack** for the planner) → `implementation-planner` (with the approved spec path; a `draft` spec or one with `[NEEDS CLARIFICATION]` → `BLOCKED`, back to `spec-creator`). Round 1, only when needed: technical decisions + execution mode, no file → main session asks the user → round 2 (writes the plan, every step cites its `AC-k`) → human sets the plan to `Status: approved` → (new chat) **single-agent:** `implementer <plan path>` / **multi-agent:** `implementer <plan path> workstream W0`, then one `implementer <plan path> workstream W<n>` per remaining `W*` workstream in parallel (production code only, no tests) → **check gate** (main session: `scripts/check.sh <pkg>` once per touched package on the combined diff; failures → implementer fix mode) → `test-writer <plan path> package <pkg>`, one per `TW-*` row in parallel (all tests, from the plan's `## Tests` table and the spec ACs) → in parallel: `plan-verifier <plan path>` ∥ `architecture-reviewer` ∥ `/code-review` (correctness bugs) ∥ `/security-review` (until a security agent exists) → **fix loop**: `implementer fix: <plan path>` with the merged findings, then `test-writer` for tests it marked wrong, then `plan-verifier` again → `doc-writer` → `/pr-self-review` → PR.

Split of responsibility: `spec-creator` answers **what and why** (all product clarification: six categories C1–C6, `[NEEDS CLARIFICATION]` markers instead of guesses). `implementation-planner` answers **how and in which order**, and never re-asks product questions. `plan-verifier` (read-only) closes the loop: every spec `AC-k`, every RQ and every step's `ACs:` trace is checked against the code.

Why `plan-verifier` runs right after the tests and not at the very end: a missing feature it finds means new code, which would invalidate the reviews and tests written on top of it. Why `architecture-reviewer` is not the bug finder: it checks layering, coupling and abstraction leaks only. Correctness bugs come from `/code-review`.

Agent changes are not planned by an agent: a human (or the main session on request) edits `.claude/agents/<name>.md` directly, following [Maintenance](#maintenance).

## Orchestration & token budget

Rules for whoever spawns these agents (the main session). They cut tokens without dropping a check: every agent keeps its preloaded skills and frontmatter model, the reviewers stay independent, and every plan item is still verified.

- **Explore once.** For a feature, either design in plan mode and hand the `implementation-planner` the approved design, or ask the `researcher` for a *context pack* (`researcher.md` → Context pack) and pass it to the `implementation-planner` verbatim. Never run broad exploration and then a planner that re-explores the same code: the planner trusts the pack's anchors and has an exploration budget (`implementation-planner.md` → Exploration budget).
- **Run `spec-creator` outside plan mode.** It must write its draft in round 1 and edit it in round 2; a read-only round 1 makes round 2 rebuild the whole file. Exit plan mode before dispatching it.
- **Relay the spec-creator's questions.** Round 1 of `spec-creator` writes a `draft` spec covering the full requested scope (design gaps, corner cases and module interactions live in the file) and returns a one-line summary, 0–4 `Clarifying questions` (scope/behaviour only) and up to 4 `UX proposals`, each with a default. Ask the user with **one** AskUserQuestion call (UX proposals as accept/reject questions if they fit), then resume the same agent (SendMessage) with the answers verbatim. Minor values are already in the spec as `assumed default — confirm`; list them at the approval gate, not as questions.
- **Spec follow-ups go through `amend:`.** Any later change to a draft spec (a correction, a confirmed default, a wording fix) → `spec-creator` with `amend: <spec path>` and the changes. It Edits in place without re-analysis. The main session never edits a spec body itself. Designs: pass local screenshot paths as they are. For a Claude Design artifact, read it in the main session first and save its HTML/screens to a local file (the scratchpad is fine), then pass that path; `spec-creator` has no network tools.
- **Ask for spec approval in chat.** When `spec-creator` returns `Ready for approval: yes`, ask the user with AskUserQuestion whether to approve it (options: approve / changes), listing its `Assumed defaults to confirm` in the question; approving confirms them. On approve, the main session changes only the `Status: draft` line to `Status: approved`; on changes, relay them to `spec-creator`. Never promote a spec without that answer.
- **Relay the spec-creator's research requests.** When `spec-creator` returns `## Research requests` (`R1`…`R4`, no file written), launch one `researcher` per request **in the same message**, passing the request line verbatim. `model: haiku` is fine only for a pure file-location request. When all reports are back, resume the same `spec-creator` (SendMessage) with every report verbatim, labelled `R<n>`. At most one research round per spec round; `spec-creator` turns what is still unknown into open questions.
- **Relay the planner's questions.** The planner doesn't clarify requirements. Round 1 (skipped when the execution mode is passed and nothing technical is open) returns `Requirements (mapped)` (RQ ← AC), non-blocking `Spec issues`, 0–3 `Technical decisions` with defaults and `Execution mode`, and writes no file. Ask the user (AskUserQuestion, keeping options and defaults), then resume the same planner (SendMessage) with the answers verbatim. A `BLOCKED — back to spec-creator` result goes to `spec-creator` round 2 (or a new round 1) with the listed markers or conflicts, never to the planner with an answer.
- **Pass paths, not content.** Between agents pass only the plan path, the diff base and, for reviewers, the implementer's `Deviations` list. Never paste a diff or a full report into another agent's prompt; agents read the repo themselves.
- **Check the budget first, then pick models.** Before a long workflow (spec → plan → implement → tests → verify), look at the usage dashboard for your plan; the limits depend on the plan and the model, so there is no universal number here. Default models (frontmatter) are chosen as the cheapest that does the role well:

  | Agent | Default | Why | Override |
  |---|---|---|---|
  | spec-creator | sonnet | template-driven analysis + EARS; questions go to the user anyway | `model: opus` for a large or ambiguous feature (many flows, conflicting designs) |
  | implementation-planner | opus | sequencing, layering and parallel workstreams across packages; mistakes here cost the most downstream | — |
  | architecture-reviewer | sonnet | rule catalog + verbatim-quote self-check keep it precise; recheck mode keeps fix rounds small | `model: opus` for a large cross-package diff |
  | plan-verifier | sonnet | mechanical item-by-item checks with evidence | `model: opus` if it misreads ACs in practice |
  | implementer, test-writer, doc-writer, researcher | sonnet | execution against a fixed plan / question | `model: haiku` for a researcher context pack or pure file search |
- **First pipeline runs: limit, don't disable.** Until the dashboard shows headroom: single-agent execution mode; at most 2 agents in parallel (the `TW-*` test-writers run one after another; reviewers run as `plan-verifier` ∥ `architecture-reviewer`, then `/code-review`); e2e only for `must` ACs with `verify: e2e`, others listed as skipped with a reason; `--it` only when DB code changed. **Never** skip the check gate (typecheck + unit tests) or `plan-verifier`: without them you can't tell whether the pipeline itself works. Raise the limits once a run completes within budget.
- **Short command output.** Every test/typecheck run goes through [`scripts/check.sh`](../../scripts/check.sh). It prints one summary line per check and only the first failing lines, so the model can't forget to trim. Plan-verifier still runs every check itself. Independence is kept; log volume is not.
- **Tests run narrow, then once in full.** The implementer runs only `scripts/check.sh <pkg> --related <changed files>` once at the end (never per step, never the full suite in a workstream: parallel workstreams would fail each other's half-done files). The main session runs the **check gate** once on the combined diff: `scripts/check.sh <pkg>` per touched package, plus `--it --no-typecheck` for server when DB code changed. Test-writer and plan-verifier run their own full checks after that.
- **Tests belong to test-writer.** The implementer writes no tests (hook: [`implementer-write-guard.sh`](../hooks/implementer-write-guard.sh)). Test-writer implements the plan's `## Tests` rows (`T#`) and every spec AC with `verify: unit | integration`, and names each test with its id (`SPEC-01 AC-3: …`) so plan-verifier can map it. It derives expected values from the spec before reading the code, and never from production constants. Pass it the implementer's `Failing existing tests` that are marked "intended behaviour change", so it updates them.
- **Fix loop, one pass at a time.** Merge the check-gate failures, plan-verifier `partial`/`not met` rows, architecture-reviewer CRITICAL/WARNING findings, `/code-review` findings and test-writer `Suspected production defects` into one numbered list (`F1 … — source — file:line — one line`). Pass it to `implementer fix: <plan path>`; it doesn't re-run the whole plan. Its `not fixed — test is wrong` rows go to test-writer, and `needs human` rows go to the user. Then re-run `plan-verifier` (and the reviewer whose findings were fixed — `architecture-reviewer` in `recheck:` mode, so only the fix delta is reviewed). Stop after two fix rounds, or as soon as a finding fingerprint (`source:rule:file`) comes back after being fixed (oscillation), and ask the user. `/run-plan` implements this loop with a ledger, waivers and backlog.
- **Compact reports, summarised once.** The implementer report stays ≤ ~60 lines; the plan-verifier prints one line per `met` row and full detail only for gaps. The main session summarises a report and links its source; it does not re-render it.
- **Parallel where independent.** `plan-verifier`, `architecture-reviewer`, `/code-review` and `/security-review` run in parallel after the test-writers, and the `TW-*` test-writers run in parallel with each other; sequential steps (context pack → implementation-planner → implementer) are not split across extra agents.
- **Multi-agent execution follows the plan's `## Execution` table.** Run `W0` alone first; then start one `implementer` per remaining workstream in the same message. Wait for all of them, run the check gate, then one `test-writer <plan path> package <pkg>` per `TW-*` row in the same message, then the reviewers and `plan-verifier` once on the combined diff. A `BLOCKED` / `PARTIAL` workstream stops the chain until it is resolved. Single-agent: one `implementer` with no workstream, then the same gate → test-writer → review sequence.
- **Dev DB after a migration.** If the implementer report has a `Dev DB` line, apply that migration to the shared dev DB (the `server/INSIGHTS.md` procedure) before anyone opens the UI.

Spec lifecycle, layout and IDs: [`specs/README.md`](../../specs/README.md). Plan lifecycle and naming: [`docs/plans/README.md`](../../docs/plans/README.md). Feature docs written by `doc-writer`: [`docs/features/README.md`](../../docs/features/README.md).

| [doc-writer](doc-writer.md) | Documents implemented features with Mermaid diagrams (`docs/features/<slug>.md` by default, module READMEs/docs when needed); every claim verified against code. | sonnet | 40 |

- No agent spawns subagents or invokes skills at runtime (`spec-creator` asks the main session for `researcher` runs instead).
- `implementation-planner` and `implementer` preload the **same** 11 implementation skills via `skills:`; the planner adds `ears-requirements` to read the spec's AC lines. `security` and `pr-self-review` are deliberately excluded — review belongs to separate agents.
- `test-writer` preloads 9 of them (no `react-best-practices` / `postgresql-table-design`: production-code design rules, not test rules).
- `architecture-reviewer` preloads engineering-insights, onion-architecture, frontend-architecture, next-best-practices, fastify-best-practices, typescript-expert.
- `doc-writer` preloads mermaid-diagram, engineering-insights, onion-architecture, frontend-architecture.
- `plan-verifier` preloads only `ears-requirements` (how an `AC-k` is read and counts as met); no best-practice skills on purpose — they invite generic advice instead of criterion-by-criterion verification.
- `researcher` has no preloaded skills.
- `spec-creator` preloads engineering-insights (read half) and ears-requirements (AC rules); its threat checklist is inlined instead of preloading `security`. The spec template, NFR checklist, traceability rules and research format live in [`.claude/reference/spec-creator.md`](../reference/spec-creator.md), read only when writing a new spec or a full rewrite. A spec states behaviour, so implementation skills would pull it towards a plan.
- Full agent → skills table: [`.claude/skills/README.md`](../skills/README.md#agent--preloaded-skills).

## Maintenance

- **New implementation skill** → add it to the Routing table in `.claude/skills/README.md` **and** to `skills:` in both `implementation-planner.md` and `implementer.md` (the lists must stay identical).
- **Plan template change** → edit `implementation-planner.md`; the implementer relies on its section names (`Status`, `Files`, `Change`, `Acceptance`, `Tests`, `Depends on`, `Modules`, `Execution mode`, `## Execution`, `[workstream: W#]`), and `plan-verifier` relies on `Requirements (verified)`, `ACs`, `Covers`, `Tested by` and `## Tests`, and test-writer relies on `## Tests` and the `TW-*` rows, so update `implementer.md`, `test-writer.md` and `plan-verifier.md` (its Step 1 ID families) too.
- **test-writer / doc-writer allowed paths change** → update the hook **and** the Permissions row here **and** the agent's Hard constraints. A test-writer path change also goes into `implementer-write-guard.sh` (it denies exactly that list).
- **`scripts/check.sh` flags change** → update the implementer Step 3, test-writer Step 5, plan template `## Verification` and the `verifier` profile of `readonly-bash-guard.sh`.
- **New architecture rule** → add it to the rule catalog in `architecture-reviewer.md` with its category (`layer` / `coupling` / `leak`).
- **Spec template change** (`.claude/reference/spec-creator.md`) → `implementation-planner` relies on `AC-k`, `Non-goals`, `Module interactions`, `Untrusted inputs` and `Open questions`; `plan-verifier` relies on `## Acceptance criteria (EARS)` and the `(removed)` marker; the hook relies on the `Spec ID:` / `Status:` lines. Update `specs/README.md` too.
- **Plan Verification command change** (implementation-planner template) → update the `verifier` profile in `readonly-bash-guard.sh`, or plan-verifier rows become `not verifiable`. Re-run the hook's piped-JSON regression checks (listed in the header of `readonly-bash-guard.sh`).
- **Read-only agent needs a new Bash command** → add it to the hook allowlist **and** the Permissions row here **and** the agent's Hard constraints.
- **New devdigest MCP tool** (`mcp/`) → decide whether it is read-only system state (add to spec-creator `tools:` and the Permissions row) or has side effects / cost (add to its `disallowedTools`).
- **New agent** → create `.claude/agents/<name>.md` directly (closest existing agent as the pattern; a fail-closed hook if it writes files) and add a row to the Catalog, Permissions and Inputs/outputs tables here.
- Don't copy agent procedures or templates into this README — link to the agent file instead.
