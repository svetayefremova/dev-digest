# PR Self Review

Reviews the whole branch diff against `main`, runs only the domain skills relevant to the files actually touched, and renders one verdict: `BLOCKED` (≥1 CRITICAL finding — do not open/merge the PR) or `OK` (safe to proceed). This skill is the thing standing between "diff looks done" and "diff is safe to ship" — treat the BLOCKED verdict as a real stop, not a suggestion.

Arguments (from `/pr-self-review [--override "<reason>"] [--force]`):
- no args — normal run (cache-aware, see Step 1).
- `--override "<reason>"` — record an explicit, audited override for the *current* diff hash (Step 6). Does not skip the review; the review still runs and still reports findings, it just also writes the override record.
- `--force` — ignore the cache and re-run the full review even if a cached verdict exists for this diff hash.

## Step 1 — Determine the diff and check the cache

```bash
BASE=$(git merge-base main HEAD)
DIFF_HASH=$(git diff "$BASE" | sha256sum | cut -d' ' -f1)
CACHE_FILE=".claude/pr-review-history/${DIFF_HASH}.json"
```

`git diff "$BASE"` (one ref, not a range) compares the merge-base against the **working tree**, so it covers committed branch work *and* uncommitted/staged changes in one pass — exactly the full scope that would land in the PR.

- If `git diff "$BASE"` is empty → report "nothing to review" and stop. No verdict, no cache write.
- If `$CACHE_FILE` exists and `--force` was not passed → read it and skip straight to Step 7 (render the cached verdict). This is the fast path: a user re-running `gh pr create` after a prior BLOCKED verdict, with no new commits, should not re-trigger a full LLM review pass.
- Otherwise continue to Step 2 for a full run.

## Step 2 — Categorize changed files into domains

```bash
git diff --name-only "$BASE"
```

Match each path against the table below. A file can match more than one domain (e.g. a Fastify route file is both `backend-architecture` and `backend-api`). Skip lockfiles, autogenerated migrations, and snapshot files entirely — they are not reviewable content (`package-lock.json`, `pnpm-lock.yaml`, `server/src/db/migrations/**/*.sql` when autogenerated by drizzle-kit, `**/*.snap`).

| Domain | Path globs | Skills to invoke |
|---|---|---|
| UI | `client/src/app/**`, `client/src/components/**`, `client/src/vendor/ui/**`, `client/src/lib/**`, `client/src/i18n/**`, `client/messages/**` | `frontend-architecture`, `react-best-practices`, `next-best-practices` |
| UI tests | `client/**/*.test.{ts,tsx}`, `client/**/__tests__/**` | `react-testing-library` |
| Backend architecture/layering | `server/src/modules/**`, `server/src/adapters/**`, `server/src/platform/**`, `reviewer-core/src/**` | `onion-architecture` |
| Backend API/routes | `server/src/modules/**/routes.ts`, Fastify plugins under `server/src/platform/**` | `fastify-best-practices` |
| Backend DB/schema | `server/src/db/**`, `server/src/modules/**/repository.ts` | `drizzle-orm-patterns`, `postgresql-table-design` |
| Shared/Zod contracts | `server/src/vendor/shared/**`, any `*.schema.ts` | `zod` |

Files outside this table (e.g. `e2e/**`) get no domain skill — only the always-on checks in Step 3 apply to them.

## Step 3 — Always run, on the full diff, regardless of domain

- Native `/code-review` at effort `medium`, scoped to this diff.
- Native `/security-review`, scoped to this diff.
- Project `security` skill (OWASP-based), scoped to this diff.

These three catch cross-cutting bugs and vulnerabilities that no single domain skill would see.

## Step 4 — Run the matched domain skills, scoped to their files only

For each domain present in the diff (Step 2), invoke its skill(s) with **only the files matching that domain** — not the whole diff. Do not invoke a skill whose domain has zero matched files in this diff; irrelevant skill runs add latency and noise, not signal.

Invoke matched domain skills **in parallel** (e.g. as parallel forks/subagent calls), not sequentially — this review runs synchronously inside a hook that blocks `gh pr create`, so wall-clock latency matters. Respect the time budget from Step 4b.

### Step 4b — Time budget (fail-open on timeout)

The whole run (Step 3 + Step 4 combined) has a total budget of **180 seconds**. Split it roughly evenly across the invoked skill passes (always-on checks + matched domain skills), with a floor of 30s per pass. If the overall budget is exhausted before every pass finishes:

- Stop waiting on unfinished passes.
- Proceed to Step 5 with only the findings collected so far.
- Mark the eventual verdict record `"incomplete": true`.
- The rendered verdict (Step 7) must say explicitly that the review did not finish and which passes didn't complete — never silently present a partial review as a complete one.
- An incomplete run **does not** force BLOCKED by default — fail open: if nothing CRITICAL was found in the passes that *did* complete, verdict is `OK` with the incomplete warning attached. The missing coverage is a known gap, not grounds to block on nothing.

## Step 5 — Normalize severity to a single scale

Every finding from every pass gets mapped into exactly one of `CRITICAL` / `HIGH` / `MEDIUM`. This is the part that makes the gate meaningful — be strict and literal about the CRITICAL bar, don't let it drift to "anything that looks bad."

**CRITICAL** — a finding is CRITICAL only if at least one of these is true:
- It would cause a runtime crash, unhandled exception path, or hang in a normal (non-adversarial) code path.
- It causes data loss or data corruption (e.g. a migration that drops data without backfill, a write that can silently overwrite unrelated rows).
- It's a security vulnerability with attacker-controlled input reaching it (injection, auth bypass, secret leak, broken access control) — i.e. whatever the `security` skill or native `security-review` already marks as HIGH confidence in an exploitable category.
- It breaks the onion-architecture dependency rule in a way that reaches production code (a route handler importing Drizzle/an adapter directly, bypassing its service/repository port) — not a test helper or a documented exception.
- It breaks a public contract/API that other code already depends on (changes a shared Zod schema's shape in a way that breaks existing consumers, removes/renames an exported route without updating callers).
- `react-best-practices` already tagged it `CRITICAL` in its own taxonomy — pass that through unchanged.

**HIGH** — a real, fixable violation of project convention or likely-but-not-certain correctness bug that does not meet the CRITICAL bar above (e.g. a non-exploitable logic bug, a significant architecture smell that doesn't cross the dependency boundary, a MEDIUM-confidence security finding).

**MEDIUM** — style, naming, minor convention drift, anything that wouldn't block a careful human reviewer either.

When a sub-skill's own native scale doesn't map cleanly, err toward the lower bucket (HIGH, not CRITICAL) unless the finding clearly matches one of the bullet points above — the point of this gate is to block real risk, not to relitigate every stylistic skill opinion as a merge-blocker.

## Step 6 — Check for an override, then decide the verdict

Before finalizing: if this run was invoked with `--override "<reason>"`, write `overridden: true`, `overrideReason: "<reason>"`, `overriddenAt: <now>` into the record that gets saved in Step 7 — regardless of what the verdict would otherwise be. The override is scoped to this exact `DIFF_HASH`; it does not carry forward to any future diff (a new commit changes the hash, so the override silently stops applying — this is intentional, not a bug).

Decide the verdict:
- `findings` contains ≥1 `CRITICAL`, and no override is recorded → **`BLOCKED`**.
- `findings` contains ≥1 `CRITICAL`, and an override *is* recorded for this diff hash → verdict stays `BLOCKED` in the record (for honesty/audit), but the override lets the PreToolUse hook allow the command anyway while surfacing the override reason as a visible warning.
- Otherwise → **`OK`**.

## Step 7 — Write the cache record and render the report

Write (or overwrite) `$CACHE_FILE`:

```json
{
  "diffHash": "<DIFF_HASH>",
  "baseBranch": "main",
  "checkedAt": "<ISO timestamp>",
  "verdict": "BLOCKED | OK",
  "incomplete": false,
  "overridden": false,
  "overrideReason": null,
  "overriddenAt": null,
  "findings": [
    { "file": "...", "line": 0, "severity": "CRITICAL|HIGH|MEDIUM", "domain": "...", "skill": "...", "summary": "...", "failureScenario": "..." }
  ]
}
```

Create `.claude/pr-review-history/` if it doesn't exist. This directory is local review state, not source — it belongs in `.gitignore`, not in the PR itself.

Render the human-facing report, grouped by domain/skill, findings sorted most-severe first, each with `file:line`, severity, one-sentence summary, and failure scenario — same field shape as `ReportFindings` uses elsewhere in this codebase.

End the response with exactly one of:

```
🚫 BLOCKED — <N> critical finding(s). Do not open/merge this PR until fixed (or run with --override "<reason>" if this is a deliberate, audited exception).
```
or
```
✅ Ready for PR — <summary of HIGH/MEDIUM notes, if any>
```
or, when incomplete:
```
⚠️ Review incomplete (<which passes didn't finish>) — no CRITICAL findings in what did complete, proceeding as OK. Re-run for full coverage.
```

When BLOCKED and not overridden: do not run `gh pr create`, `gh pr merge`, or `git push` in this same turn, even if the user asked for it earlier in the same request. Say plainly that it's blocked and what needs to change, or that `--override` is available if this is a deliberate exception.

## Headless / machine-readable output contract

When this skill is invoked non-interactively (e.g. `claude -p` from the PreToolUse hook), the final message MUST end with a fenced block exactly like this, in addition to the human-readable report above — the hook script parses this block, not prose:

```json-verdict
{"verdict":"BLOCKED","diffHash":"...","overridden":false,"incomplete":false}
```

(`json-verdict` is a literal fence-info-string tag, not a real language — it exists so the wrapper script can grep for it unambiguously instead of guessing which ` ```json ` block in the response is the verdict.)
